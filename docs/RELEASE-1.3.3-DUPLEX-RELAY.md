# 1.3.3 候选：双向转发及断流证据

此前转发循环先等待 socket 可写，再调用阻塞式 sendAll。当应用暂时不读取下载，
或代理暂时不读取上传时，send 仍可能阻塞在写入中，导致另一方向也无法传输。
本地对照和回归测试已复现两个方向的问题。

转发现在使用非阻塞 socket，每个方向最多暂存 64KiB，分别等待读写就绪。
一侧背压不会阻塞另一侧。仅有待发送数据时才计算发送停滞期限；正常空闲流
继续等待，FIN 在该方向暂存字节全部送出后传播。TLS 前缀沿用相同转发机制，
不解析、解密或修改业务内容。

调试日志保留 SYN/FIN/RST 控制包，普通 ACK 和数据包通过已有字节计数观察，
避免逐包写盘快速覆盖断流证据。每条 EOF/结束记录补充原进程、原始连接、
出口及代理 socket 元组，结束记录还包含域名策略。即使开始记录已经轮转，
也能关联结束事件。运行时日志等级改为原子读写，消除并发重载的数据竞争。

增加的回归覆盖双向背压、发送停滞期限与失败方向、堵塞时正常停止、逐包洪水
下重注入和关键记录保留，以及日志等级并发修改。此前 TLS 字节保真、半关闭、
空闲响应和截断响应的边界检查继续保留。

这些检查证明本地缺陷及修复行为，不证明外部代理或服务端的长连接恢复。
域名策略承接 [1.3.2 配置方法](RELEASE-1.3.2-TLS-CACHED-DNS.md)。安装前仍需
正常停止截流并从托盘退出；现有连接需要在新版启动后重新建立。

手工诊断目标 `aps_relay_probe` 默认不构建、不打包，也不注册自动联网测试。
它仅监听临时 loopback 端口，使用生产 RelaySession，并在指定期限内退出；
不会打开 WinDivert、读取配置或使用应用凭据。
